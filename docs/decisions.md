## S1. Temporary password scheme (`username@year`)

**Decision (user, Phase 1 change 3).** When an account is created or a password is reset or reissued, the server sets a temporary password of the form `<username>@<year>`, where the year is the current year at issue time, for example `ravi@2026`. This value does not have to meet the normal password policy; only temporary passwords get this exemption.

**This scheme is predictable.** Anyone who knows a username and the year can work out the temporary password. Between issue and first use, the account can be taken over by whoever signs in first. The limits below are the mitigation, and they are the reason this scheme is acceptable:

1. **First sign-in only.** A successful sign-in with the temporary password marks it used (`temp_password_used_at`). It cannot be used again, even if no new password was chosen.
2. **Immediate forced change.** That sign-in lands behind the onboarding or forced-change gate. `evaluate()` refuses everything else until a new, policy-compliant password is set.
3. **24-hour expiry.** `temp_password_expires_at` is issued time plus 24 hours. After that the temporary password is refused even if unused.
4. **Reissue.** The creating Project Manager (for their Authors) or the Software Administrator can reissue it. Reissuing resets the 24-hour clock, clears the used flag and revokes every session.
5. **Shown once.** It is returned to the creator in the single create, reset or approve response. It is never stored in plain text, never written to logs and never written to the audit log (the audit sanitiser drops any key resembling `password`, and no route passes it in metadata). `security-regression.js` checks the captured server log for every temporary password it was issued.
6. **Rate limit still applies.** The 10-per-15-minutes limit per username + IP covers temporary-password sign-ins exactly as it covers normal ones.
7. **Short gated session** (A4): the session that sign-in creates lasts at most 30 minutes.

Residual risk: within the 24-hour window, and before the real user signs in, someone who knows the username can sign in first. The real user would then find the temporary password already used and ask for a reissue, which revokes the other session. Distributing the temporary password out of band and signing in promptly keeps this window small. A random temporary password would remove the risk; that is a one-function change in `server/auth/policy.js` (`tempPasswordFor`) if the decision is revisited.

The bootstrap administrator's password (A7) is not a `username@year` temporary password. It comes from the environment, must meet the policy and is behind a forced change.

## Phase 5: Backup and restore

| # | Decision | Notes |
|---|---|---|
| K1 | **One recovery unit, one folder per backup**: `<backupDir>/bk-<UTC yyyymmdd-hhmmss>-<6 hex>/` holding `db/agastya.db`, `projects/<id>/…`, `snapshots/<request id>/…`, `manifest.json` (format and version, id, time, kind, who, app version, schema migrations, counts, every file with stored and original size and SHA-256) and `manifest.seal` (SHA-256 of the manifest, or HMAC-SHA256 with the backup key). A folder, not an archive: nothing is ever extracted from a container, so there is no archive-traversal surface; every path in a manifest must still match a strict pattern and resolve inside the backup. No new dependency. | `server/backup/format.js` |
| K2 | **Contents**: the whole database (accounts with password hashes, sessions, audit log, projects, documents, revisions and their content, requests, drafts, notifications, overrides), every workspace file (modules, publication module, `project.json`, front matter, graphics, soft-deleted modules) and the snapshots. **Left out**: build outputs (`output.pdf/.fo`, `jss-book.xml`, `_*` intermediates, `*-run.xsl`), the `.previews` cache and `*.tmp` files (made again by the next build), and `.env`, `vendor/`, `client/dist` (configuration and code, not data). Links and odd files are skipped and counted. | |
| K3 | **Consistency**: a maintenance gate (`server/maintenance.js`) lets in-flight writes finish, then holds new ones with 503 `MAINTENANCE` while the database is copied with `VACUUM INTO` and the files are read; reads carry on. Counts are taken from the copy itself. A restore holds every API request and WebSocket, and waits for PDF builds to finish. One operation at a time in the process, and across processes through `<backupDir>/.lock`. | Live backup of a running server |
| K4 | **Atomic and verified**: written into `.tmp-<id>`, every stored file re-read and checked, then renamed into place. A backup that is not complete is never listed; `.tmp-` leftovers are removed at start. Failures are mapped to codes with no paths (`INSUFFICIENT_STORAGE` 507 for no space, before and during; `PERMISSION_DENIED`; `BACKUP_IO_ERROR`). | |
| K5 | **Restore**: verify in full (seal, every hash, nothing unlisted, no links, schema not newer than this version, the database's integrity and foreign-key checks); stage beside the data and re-hash; migrate the staged database and compare its counts with the manifest; take and verify a **recovery point** (`pre-restore` backup) of the current state; gate; carry audit rows; swap under a journal; reopen, migrate, verify every count and every file's hash; on any failure put the original data back. A crash during the swap is undone at the next start (`server/backup/recovery.js`) before the database is opened. | |
| K6 | **Audit continuity**: audit rows written after the backup (including the restore's own start and its recovery point) are copied into the restored database with their ids, so the trail has no gap; `backup.restored` follows them. | Append-only log (C7) kept |
| K7 | **A restore ends every session** (revoked sessions in the backup must not come back to life) and asks for the backup id typed again, the administrator's **password** (rate-limited) and a **reason** (10 to 1000 characters). | |
| K8 | **Retention**: the newest `AGASTYA_BACKUP_KEEP` (default 14) scheduled backups and the newest 3 recovery points are kept, older ones deleted (audited as `backup.retention_deleted`); manual backups stay until deleted; the newest usable backup is never deleted, and the only usable one cannot be deleted by hand (409 `LAST_BACKUP`). | |
| K9 | **Who**: the Software Administrator only (`admin.backup`, 403 for everyone else). Backup folders and files are created `0700`/`0600` (POSIX; on Windows the folder's ACL applies). | |
| K10 | **Encryption**: optional AES-256-GCM per file with `AGASTYA_BACKUP_KEY` (32 bytes, hex or base64), never written into a backup or a log; the manifest records only a key id and is sealed with an HMAC. Without a key, backups are not encrypted and the health screen and Backups page say so; the SHA-256 seal then detects damage but not deliberate tampering by someone who can write the backup folder. The health screen shows the schedule, the last good backup, its age (warning after 26 hours with a schedule), damaged folders and configuration problems. Audit details are allow-listed (ids, kinds, counts, codes). | |
| K11 | **Schedule** from the server's settings (`AGASTYA_BACKUP_SCHEDULE=HH:MM`), checked every minute, once per day, retried after 30 minutes on failure; settings are not stored in the database so a restore cannot change them. The **command line** (`npm run backup -- list | create | verify | restore`) shares the code; `create` and `restore` refuse while a server uses the data folder (`server.pid`). | |
| K12 | **Limits**: backups are copies on the same machine unless `AGASTYA_BACKUP_DIR` points elsewhere (copy them off the machine); writes pause for the duration of the copy (seconds for typical data, longer for very large workspaces); a restore signs everyone out and build outputs must be rebuilt; restoring a backup made by a newer version is refused; tested on Linux only (the backup tests pass on tmpfs and on btrfs), not yet on Windows/NTFS, where read-only snapshot files and open handles behave differently. | |
| K13 | **Busy files on Windows**: renames during a backup, a restore's swap and a recovery are retried for about three seconds when the file is briefly held (`EBUSY`/`EPERM`/`EACCES`, typically an antivirus scanner or the search indexer); a hold that lasts fails safely with 503 `FILE_BUSY` and nothing replaced. The Windows procedure (secure settings, folder permissions, antivirus exclusions, golden build, a backup and restore drill on a copy of the data) is `docs/production.md`. | Not yet run on Windows |
| K14 | **Windows path checks ignore case**: the backup folder may not be, contain or lie inside the data folder however either is capitalised (`D:\Agastya\data` and `d:\agastya\DATA\backups` overlap), as NTFS treats them; the doctor's "link to a tool outside the project" note compares without case on Windows too. The backup command reads its flags wherever they are (`create --note` was ignored). | Found preparing `docs/production.md` |

## Toolchain risks

| # | Decision | Notes |

| X1 | **xsltproc is the JSS copy** (on Windows; see V12 for the Linux development machine): `libxslt-1.1.28-win32-x86`, a **2015, 32-bit** build using **libxml2 2.9.3**, which has **known published vulnerabilities**. No official newer Windows build exists (the libxml2 project publishes none). Accepted for now and mitigated by: (1) the XML safety guard on every write, so external entities and doubled documents never reach a transform; (2) xsltproc always runs with `--nonet`; (3) only authenticated authors can put content into a project. **This must be re-checked before production use.** | User, Phase 2 answer 2 |
